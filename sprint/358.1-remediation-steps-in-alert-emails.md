# Every alert email says what to do next: a remediation playbook per finding
**Difficulty:** 4

> _Added by the orchestrator on 2026-10-06 at the user's request, after they
> reviewed the 356.1 sample emails: "for some of these, it would be very nice
> to know what the remediation steps would be. Like, does any action need to
> be taken for the weekly digest information?"_

## Goal
Every alert email, and every amber or red value in the weekly digest, comes
with a **"What to do"** section. It is a short, ordered list of steps
specific to the finding: what to check first, the exact command to run, and
when it's safe to do nothing. The digest opens with a **"Needs attention"**
list, worst first, or states plainly "Nothing needs attention this week."

## Reason
The 356.1 templates show *what* is wrong very well, but leave the reader to
work out *what to do*. The user, looking at the sample digest (diner-decider
disk 93%, cert 5d, backup 3d, all in red): "does any action need to be
taken?" A red number with no next step makes the email a puzzle.

The deploy-failed sample also shows guidance that's actively misleading:
- it offers `emit-infra rollback martialops` first, while saying "the
  previous build should still be serving". A build-time TypeScript error
  never reached production, so the right advice is "fix and push again; no
  rollback needed";
- its second command, `tail -n 100 projects/martialops/.deploy-history.jsonl`,
  is a relative path that only works from `~`, and it's deploy *history*,
  not the build log.

Remediation has to fit the specific failure, not be one fixed list per kind.

## Context
- **Templates:** `apps/api/src/lib/email-templates/`, with `layout.ts`
  (facts, sections, actions, "Run:" lines), the renderers `health.ts`,
  `alert-rule.ts`, `deploy.ts` and `digest.ts`, plus `combined.ts` (356.2
  outbox), `format.ts`, `types.ts` and `fixtures.ts`. Data gathering lives
  in `apps/api/src/lib/email-context.ts` (357).
- **New pure module:** `apps/api/src/lib/remediation/`.
  - `remediate(finding) → { urgency: 'now'|'soon'|'watch'|'none', headline, steps: Step[] }`,
    where a `Step` is `{ text, command?, link? }`.
  - `finding` is a discriminated union (`disk`, `mem`, `cert`, `backup`,
    `health`, `deploy-failed`, `incidents`) carrying the same data the
    renderers already get.
  - Renderers call it and pass the result to a new layout section,
    `renderWhatToDo()`.
  - The playbook text lives here, not in the templates, so it can be tested
    and reused (e.g. the dashboard later).
- **Real commands only.** The registered CLI commands are: `setup init
  provision configure deploy status logs secrets destroy audit rollback
  versions hooks terraform-init r2:rotate-token`.
  - `logs` takes a **container** argument, not a project name. Check its
    flags in `apps/cli/src/commands/logs.ts`.
  - Raw SSH commands use `ssh root@<serverIp> '<cmd>'` with the real IP
    from the project config (all fleet tooling logs in as root; see
    `packages/core/src/ssh.ts`).
  - Paths are absolute (`~/projects/<name>/…`).
- **Playbook content.** Refine against the code and docs. Each entry needs a
  concrete first step.
  - **disk.** At ≥80% the urgency is *soon*; at ≥90%, or projected full in
    under 7 days from `computeLinearTrend`, it's *now*.
    1. See what's using space: `ssh root@<ip> 'docker system df && du -xh /var/lib/containerd /var/lib/docker --max-depth=1 2>/dev/null | sort -h | tail'`.
       Image bytes live in `/var/lib/containerd` on these servers.
    2. Prune old images. Find the prune path the deploy pipeline uses
       (aggressive prune is the blue-green default) and point to it, or give
       `docker image prune -a --filter until=168h`.
    3. Check logs and DB volume growth.
    4. If disk is still above 85% after pruning, resize the server (link
       `docs/scaling.md`).
  - **mem:** find the top containers (`docker stats --no-stream`) and check
    for a leak against the recent deploy time.
  - **cert.** Under 21 days, renewal has been failing for over a week, so
    *soon*; under 7 days is *now*. Include the certbot error if present.
    1. `ssh root@<ip> 'certbot renew --dry-run'`.
    2. Check the renewal method (webroot vs DNS-01; see diner-decider's 2026-09
       expiry in `docs/DEPLOYMENT-PITFALLS.md`).
    3. Make sure `ensure-cert-renewal.sh` is installed.
  - **backup.** Stale over 30h, or status failed, is *now*.
    1. `ssh root@<ip> 'cat /opt/<name>/.backup-status.json'`.
    2. Read the backup sidecar's logs (`docker logs --tail 50 <backup container>`).
       The container name is per project; link `docs/BACKUP-INVENTORY.md`
       if it exists yet, otherwise say "see the project's
       docker-compose.prod.yml".
    3. Trigger a manual run once it's fixed.
  - **health** (by cause, from `causeText()`):
    - connection refused or 502: container down or crash-looping. Check
      `docker compose ps` / logs, then restart.
    - timeout: server overloaded or unreachable. Run `emit-infra status
      <name>`, then check load.
    - TLS error: same steps as cert.
    - 5xx: app error. Check app logs and the most recent deploy.
    - Recovered: urgency *none*, "No action needed — consider checking what
      caused the N-minute outage", with the logs step.
  - **deploy-failed** (classify the error text):
    - Build or typecheck failure (`docker build failed`, `TS\d+`, `ERR_PNPM`,
      `exit code`) before the switch: production unaffected, no rollback.
      "Fix the error locally (`pnpm typecheck`/`pnpm build` in
      `~/projects/<name>`) and push again."
    - Transient registry or network error: "Re-push; the build retries once
      automatically (sprint 355)."
    - Health-check failure or post-switch error: *now*. "Production may be
      serving the new broken build: `emit-infra rollback <name>`, then
      investigate."
    - Show the deploy log location the pipeline actually writes (find it in
      `scripts/lib/` / `deploy-detached.sh`) instead of the history jsonl.
  - **incidents (digest):** 1 or more in the week is *watch*, 3 or more is
    *soon*. "Review the incident timeline in the dashboard; repeated
    short outages usually mean a crash loop or memory pressure."
- **Digest changes (`digest.ts`):**
  - A "Needs attention" section above the per-project table: one row per
    amber/red finding, sorted *now* → *soon* → *watch*, each with its
    headline and first step.
  - The full steps sit in per-project "What to do" sub-sections below the
    table.
  - Healthy week: a green tone and "✅ Nothing needs attention this week."
  - The tone follows the worst finding: any red makes it critical. The
    sample was amber with three red cells.
- **Push bodies** also gain the first step's text, truncated, so the phone
  notification is actionable.

## Acceptance criteria
- [ ] `remediation/*.test.ts` covers, per kind, each urgency boundary (disk
      79/80/90 and projected <7d; cert 21/7; backup 30h and failed), and
      health cause → first step mapping. Deploy classification covers a TS
      build error (no rollback suggested), a registry error (re-push) and a
      post-switch health failure (rollback is the first step).
- [ ] A test asserts that every `emit-infra <subcommand>` appearing in any
      remediation command is a registered CLI command (read the names from
      the CLI's commander setup or a shared list), and that no command uses
      a relative `projects/` path.
- [ ] `digest.test.ts` covers that the 3-red fixture gets a critical tone,
      "Needs attention" lists the findings worst-first with a first step,
      and the healthy fixture says "Nothing needs attention this week".
- [ ] `deploy.test.ts` covers that the build-failure email does not contain
      `emit-infra rollback` as a step and does contain "no rollback needed".
- [ ] The text versions contain the What-to-do steps.
- [ ] Sample emails delivered (`devel logs`), recorded in Completed.
- [ ] `pnpm test`, `pnpm typecheck` and `pnpm lint` pass.

## Out of scope
- Auto-remediation (running any of these commands automatically).
- Dashboard UI for remediation, though the module is designed so it can be
  reused there later.
