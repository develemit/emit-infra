# Coalescing email outbox: alert bursts become one email, never dropped
**Difficulty:** 4

> _Written by /start-sprint-auto to clear sprint 356.1's blocker, 2026-10-06._

## Goal
Alert emails go through a small outbox in the emit-infra API. The first
alert sends immediately. Anything that fires within the next 5 minutes is
held and sent as **one combined email** when the window opens, using the
356.1 layout with a section per alert. No alert email is ever silently
dropped because of develemail's per-recipient cooldown.

## Reason
Sprint 356.1's blocker, verbatim:

> `[blocker]` develemail rejects a second email to the same recipient within
> 5 minutes (HTTP 429, surfaced by the SDK as the misleading "idempotency key
> is currently being processed"). Sprint 357 routes every alert through
> `notify()`, so a burst (e.g. several projects down at once) will drop all
> but the first email. 357 needs per-project batching or a different
> delivery approach before it ships.

Root cause, confirmed by reading the develemail source on 2026-10-06:
- `~/projects/develemail/apps/api/src/app/wiring/messaging.ts:99` hardcodes
  `recipientCooldownMinutes: 5` for every project. `checkCooldown()` in
  `domains/emails/guardrails.ts:238` throws `RecipientCooldownError`, which
  becomes a 429.
- `@develemail/sdk@0.4.0` treats 429 as retryable (`dist/index.js:23`) and
  retries with the **same** `Idempotency-Key`. The retry hits develemail's
  in-flight idempotency record and gets a 409 "currently being processed".
  That's the message the user sees.
- There's also a 5-minute **dedup** window on identical from+to+subject
  (`guardrails.ts:159`), which returns `duplicate: true` without sending.
  Identical reminder subjects would be swallowed silently.

Coalescing is the right behaviour regardless of develemail's limits: when
four projects go down at once, one email listing all four reads better than
four separate ones.

## Context
- **Pieces from earlier sprints:**
  - `apps/api/src/lib/notify.ts`: `notify()`, with a structured `email`
    field from 356.1;
  - `apps/api/src/lib/email.ts`: `sendEmail()`;
  - `apps/api/src/lib/email-templates/`: `layout.ts` and the per-kind
    renderers (`health`, `alert-rule`, `deploy`, `digest`).
- **The API is a single long-lived local process** (launchd `com.emit.infra`,
  restarted with `pnpm launch`). An in-memory outbox is fine for the timing
  logic, but **persist pending items** to `~/.emit-infra/email-outbox.json`
  (0600), so a restart inside the window doesn't lose them. Flush any
  pending items on startup.
- **Outbox rules:**
  - Track `lastSentAt`. If more than 5m15s have passed (the 15s is margin),
    send now.
  - Otherwise enqueue, and schedule a flush for `lastSentAt + 5m15s`.
  - On flush:
    - 1 pending item → send it as-is;
    - several → send one combined email with subject `[emit-infra] 🔴 N
      alerts — tastease DOWN, martialops cert 6d, …` (truncated to a sane
      length);
    - each item's rendered body becomes a section, worst tone first, so the
      combined email's tone is the worst one.
  - If develemail still answers with cooldown (429 or 409) or `duplicate:
    true`, requeue and retry at the next window. **Never drop.** After 3
    failed windows, log an error and keep the item. Push still went out.
  - Weekly-digest (`info`) items join the same outbox.
- **Dedup safety:** develemail swallows an identical subject within 5
  minutes. Combined emails have unique subjects, and reminder subjects
  include the duration ("still down 45m"), so they differ. Assert this in
  tests rather than relying on it silently.
- **SDK retries:** construct the client so 429 isn't blindly retried with
  the same key. Check whether `@develemail/sdk` accepts `maxRetries` or a
  similar option. If it doesn't, catch the error, classify a message
  containing `idempotency` / `429` / `cooldown` as cooldown, and let the
  outbox handle the retry.
- **Config:** read the window from `ALERT_EMAIL_MIN_INTERVAL_SEC` (default
  315) so it can follow develemail if its cooldown changes.

## Completed

**Date:** 2026-10-06

### Summary
Added `email-outbox.ts`: the first alert email sends immediately; anything within the window (`ALERT_EMAIL_MIN_INTERVAL_SEC`, default 315s, plus 15s margin) is queued, persisted to `~/.emit-infra/email-outbox.json` (0600, atomic rename) and sent as one combined email when the window opens (`combined.ts`: worst tone first, subject `[emit-infra] 🔴 N alerts — …` truncated to 120 chars, text version joins every item). A single pending item is sent as-is. Retryable failures (429, idempotency-conflict, `duplicate: true`) requeue and retry each window, never dropping; after 3 failed windows an error is logged and the items are kept. Startup (`index.ts`) loads the file and flushes overdue items. `notify()` now enqueues instead of sending; `NotifyResult.email` is `{queued:true}` or the send result.

Design notes: `RenderedEmail` gained an optional `tone`, set by the health/alert-rule/deploy/digest renderers, so the outbox can sort without parsing subjects (notify falls back to severity). The SDK client is built with `maxRetries: 0`, so a 429 surfaces as a cooldown for the outbox instead of the misleading 409. Combined HTML nests each item's body (extracted from its full document) rather than re-rendering from structured data. Any send failure (not just retryable) pushes `lastSentAt` forward so the flush timer can't spin.
