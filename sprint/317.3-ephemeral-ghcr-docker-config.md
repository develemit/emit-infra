# Make the blue-green GHCR login ephemeral so it leaves no credential at rest
**Difficulty:** 3

## Goal
A blue-green deploy authenticates to ghcr.io into a throwaway Docker config
directory that is removed when the deploy finishes, success or failure.
`/root/.docker/config.json` gains no `ghcr.io` entry, so sprint 320's cleanup
stays clean instead of being undone by the next deploy.

## Reason
Sprint 317 added the login task and fixed the real functional bug: blue-green
deploys can now pull private images on a server that has never had a manual
`docker login`. But the task it added is a plain
`docker login ghcr.io`, which writes `/root/.docker/config.json` and leaves it
there permanently.

That makes sprint 320 self-defeating. 320 removes the persistent credential
from every fleet server; the very next deploy writes the same broad-scope
`gho_` token straight back into the same file. The end state 320 exists to
reach — no long-lived GitHub credential at rest on any fleet server — is never
actually reached. It becomes a one-time cleanup that undoes itself.

Verified 2026-08-27 against `7c941cc` (sprint 317's commit):
- The login task is plain `docker login ghcr.io`, no `--config` override.
- There is no `docker logout`, no `DOCKER_CONFIG`, and no cleanup task
  anywhere in `deploy-blue-green.yml` or `blue-green-deploy.sh`.
- The token is still the broad one — `deploy.ts:175` passes `ghcr_token`,
  sourced from `gh auth token` at `pre-push:191`, carrying `repo`, `user`,
  `workflow`.

This was caught in review by the martialops project against emit-infra at
`591fbbe`, and the correction is theirs.

Note this does **not** resurrect sprint 319. The token in flight is still
broad-scope, and narrowing it to `packages: read` with a one-hour expiry is
still 319's job, still deferred, still optional. What this sprint fixes is the
*at rest on disk indefinitely* half of the problem, which is the half 320
promises to deliver.

## Context

### emit-infra already has the right pattern — on the workstation side
`scripts/hooks/pre-push:195-200` does exactly this and has for some time:

```bash
DOCKER_CI_CONFIG="${TMPDIR:-/tmp}/emit-docker-ci"
mkdir -p "$DOCKER_CI_CONFIG"
if [[ -d "$HOME/.docker/cli-plugins" && ! -e "$DOCKER_CI_CONFIG/cli-plugins" ]]; then
  ln -s "$HOME/.docker/cli-plugins" "$DOCKER_CI_CONFIG/cli-plugins"
fi
echo "$TOKEN" | docker --config "$DOCKER_CI_CONFIG" login ghcr.io -u "${GHCR_USER:-$GHCR_ORG}" --password-stdin
export DOCKER_CONFIG="$DOCKER_CI_CONFIG"
```

Port the same idea to the server side. Prefer this over adding a
`docker logout` task after the deploy: a logout leaves the credential behind
whenever the deploy dies between login and logout, which is precisely when
things are already going wrong.

### The pull happens in a separate process
`deploy-blue-green.yml` invokes
`command: bash {{ app_dir }}/blue-green-deploy.sh {{ project_name }}`, and the
actual `pull` is inside that script (`blue-green-deploy.sh:177`,
`$(compose_cmd_inactive) pull`). So exporting `DOCKER_CONFIG` in the login
task's own shell accomplishes nothing — each Ansible task is a separate
process. It must be set on the **script-invocation task's** `environment:`.

The login task is currently the only `docker` invocation in
`deploy-blue-green.yml` itself; everything else goes through the script.

### The backward-compatibility trap — do not skip this
`when: ghcr_token is defined` is load-bearing. Sprint 317 verified both paths
with real diner-decider deploys: with a token (login runs) and without (task
skips, deploy still succeeds using the server's existing persistent
credential). Fleet servers still have that persistent file until 320 runs, so
the no-token path must keep working.

That means `DOCKER_CONFIG` must **not** be set when `ghcr_token` is undefined.
Pointing it at an empty or non-existent directory would hide the persistent
credential and break exactly the projects 320 hasn't reached yet. A
conditional environment mapping expresses this directly, e.g.

```yaml
environment: "{{ {'DOCKER_CONFIG': ghcr_config_dir} if ghcr_token is defined else {} }}"
```

Verify whichever form you choose actually omits the variable rather than
setting it empty — an empty `DOCKER_CONFIG` is not the same as an unset one.

### Cleanup must survive failure
Use `block:` / `always:` so the ephemeral directory is removed whether the
deploy succeeds or fails. A deploy that dies mid-pull must not leave a
credential behind — that is the whole point of choosing this approach over a
trailing logout.

### Where to put the directory
Somewhere per-deploy and predictable enough to clean up, e.g. under `/root/`
or `/tmp` keyed by project name. Avoid a fixed shared path if two projects can
deploy concurrently on one host — sprint 320's context notes some servers host
more than one thing. Set restrictive permissions (`0700`); the file written
inside is a credential.

### Keep `no_log: true`
The login task must keep it. It is what stops the token appearing in Ansible's
task output. (It does *not* stop the token appearing in a failed
`ansible-playbook` process error — that is sprint 317.1's separate fix.)

## Tasks
1. Wrap the GHCR login and the blue-green script invocation in a `block:` with
   an `always:` cleanup.
2. Create the ephemeral config directory (mode `0700`, project-scoped path)
   before the login, only when `ghcr_token is defined`.
3. Change the login task to `docker --config <dir> login ghcr.io …`, keeping
   `no_log: true` and the `when: ghcr_token is defined` guard.
4. Set `DOCKER_CONFIG` on the script-invocation task's `environment:`, only
   when `ghcr_token is defined`. Confirm the unset-vs-empty distinction.
5. Remove the directory in `always:`.
6. Verify against a real deploy on a blue-green project **with** a token:
   the pull succeeds, and afterwards `/root/.docker/config.json` has no
   `ghcr.io` auth entry that the deploy added, and the ephemeral directory is
   gone. Compare by key presence — never echo the auth blob.
7. Verify the **no-token** path still works: the login task skips, the deploy
   still succeeds on the server's existing persistent credential, and
   `DOCKER_CONFIG` is not set for the script.
8. Update `sprint/320-retire-persistent-server-ghcr-creds.md`: correct its
   claim that a post-deploy entry is "short-lived and expected", and add this
   sprint to its gate alongside 317.

## Files involved
- `ansible/roles/app-deploy/tasks/deploy-blue-green.yml` — block/always,
  ephemeral config dir, `--config` on login, `DOCKER_CONFIG` on the script task
- `ansible/roles/app-deploy/files/blue-green-deploy.sh` — read-only; confirm it
  does not override `DOCKER_CONFIG` or call `docker --config` itself
- `scripts/hooks/pre-push` — read-only reference for the established pattern
- `sprint/320-retire-persistent-server-ghcr-creds.md` — correct the
  "short-lived entry" claim and the gate
- `ansible/roles/app-deploy/tasks/deploy-standard.yml` — read-only. It has the
  same persistent-login shape; note whether it needs the same treatment as a
  follow-up rather than changing it here.

## Acceptance criteria
- [ ] After a real blue-green deploy with a token, `/root/.docker/config.json`
      contains no `ghcr.io` auth entry added by that deploy — shown by key
      presence, never by printing the value.
- [ ] The ephemeral config directory does not exist after the deploy, on both
      the success path and a deliberately failed one.
- [ ] The pull still succeeds with a token — a real deploy, not a dry run.
- [ ] The no-token path is unchanged: login skips, deploy succeeds on the
      existing persistent credential, `DOCKER_CONFIG` unset for the script.
- [ ] `no_log: true` is still present on the login task.
- [ ] Sprint 320's "short-lived entry" claim is corrected and its gate names
      this sprint.
- [ ] `pnpm test` and `pnpm typecheck` clean (no TS changes expected, but the
      repo's verification still runs).

## Out of scope

- `deploy-standard.yml`'s equivalent persistent login. No fleet project uses

  note it as a follow-up.
- Sprint 320's fleet operation itself.
