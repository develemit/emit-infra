# Redact secret-shaped values from the deploy dry-run plan printer
**Difficulty:** 3

## Goal
`emit-infra deploy --dry-run` prints its extra-vars plan with every
secret-shaped value replaced by a redaction marker, including values nested
inside objects. The plan stays useful — keys, structure, and non-secret values
are all still visible — but no credential is printed.

## Reason
`printDryRunPlan` ends with `console.log(JSON.stringify(extraVars, null, 2))`,
which dumps every extra-var verbatim. During sprint 317 a child ran
`emit-infra deploy --dry-run` to inspect the plan and printed the operator's
live `gh auth token` into a session transcript; three occurrences of a real
`gho_` token were confirmed on disk in the session JSONL afterwards. That token
carries `repo` scope — full read/write to every private repository on the
account.

Dry-run is the one command people reach for *because* it is supposed to be the
safe, side-effect-free way to inspect a deploy. Printing live credentials is
exactly the opposite of that promise, and it is the reason someone runs it with
output captured.

This is a separate defect from sprint 317.1. That sprint stops secrets reaching
error messages on failure by not including the command line at all. Here the
output is deliberate — we *want* to print the plan — so suppression is not an
option and redaction is the correct tool.

## Context

### Where it is
`apps/cli/src/commands/deploy.ts`, in `printDryRunPlan`:
```ts
console.log(chalk.bold('\nAnsible extra-vars:'))
console.log(JSON.stringify(extraVars, null, 2))
```
Everything above that line prints specific, already-safe fields (compose paths,
env file key *counts*, slot ports). Only this final dump is unfiltered.

### What actually flows through extra-vars — grep, do not assume
Confirmed present as of 2026-08-26; re-derive rather than trusting this list:

| Key | Set in | Shape |
|---|---|---|
| `ghcr_token` | `deploy.ts:175` | top-level string |
| `cloudflare_api_token` | `configure.ts:32`, `setup.ts:242` | top-level string |
| `r2_credentials` | `setup.ts:258` | **nested object** |

`r2_credentials` is the important one: it is a `Record<string, string>` built at
`setup.ts:179-196` holding `CF_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`,
`R2_SECRET_ACCESS_KEY`, and per-bucket `R2_<PREFIX>_SECRET_ACCESS_KEY` entries.
**A flat top-level key filter silently misses all of them.** The helper must
recurse.

Note the per-bucket keys are dynamically generated from bucket names
(`setup.ts:193`), so an exact-match allowlist of key names cannot work — match
on shape (substring/pattern) rather than enumerating.

### Design notes
- Put the helper in `packages/core` (e.g. `packages/core/src/redact.ts`) and
  export it from `packages/core/src/index.ts`, so a future caller that needs to
  print extra-vars has one obvious thing to reach for. Follow the existing
  export style in that index.
- Return a redacted **copy**; never mutate the caller's object. `extraVars` is
  passed to `runAnsible` right after the dry-run check in some flows, and
  mutating it would ship redaction markers to the actual playbook.
- Redact the *value*, keep the *key*. `"ghcr_token": "<redacted>"` tells the
  operator the token was present and wired, which is exactly what a dry run is
  for. Dropping the key entirely would make a missing token and a present one
  look identical.
- Consider preserving a hint that costs nothing — e.g. a fixed marker like
  `<redacted>` — but do **not** print a prefix, suffix, or length, since those
  narrow a brute-force search.
- Match case-insensitively on substrings like `token`, `secret`, `password`,
  `key`, `credential`. Be careful with `key`: `ssh_key_name`, `sshKeyName`, and
  `zone_id`-adjacent fields are *names*, not secrets, and redacting them makes
  the plan misleading. Decide deliberately and write a test pinning whichever
  way you choose, with a comment explaining it.

### Where it is called
`deploy.ts:299-303` builds extra-vars then calls `printDryRunPlan` when
`--dry-run` is set. There is one call site today; the helper exists so a second
one cannot reintroduce the leak.

### Test conventions
`apps/cli/src/commands/deploy.test.ts` already covers `buildDeployExtraVars`
(see its `GHCR_TOKEN: 'tok'` case at :109). Unit-test the helper in
`packages/core` next to its implementation, and assert the printer's behaviour

## Completed

**Date:** 2026-08-27

### Summary
Added a shared `redactSecrets` helper in `packages/core` and wired it into
`printDryRunPlan`'s final `JSON.stringify(extraVars, …)` dump, the only line
in that function that printed unfiltered data (the earlier lines only print
paths, existence checks, and env-file key counts, which were already safe —
confirmed by re-reading them line by line).

Re-derived the secret-bearing extra-vars by grep: `ghcr_token` (top-level
string, `deploy.ts:174`) and `cloudflare_api_token` / `r2_credentials`
(`configure.ts:34`, `setup.ts:243`/`258` — not currently reachable through
`deploy --dry-run`'s call site, but the table in this sprint's Context section
matched what's in the code today). `r2_credentials` is a flat
`Record<string, string>` mixing a non-secret `CF_ACCOUNT_ID` with several
secret values (`R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, and per-bucket
`R2_<PREFIX>_ACCESS_KEY_ID` / `R2_<PREFIX>_SECRET_ACCESS_KEY`).

Key design decision: redaction is decided per-value by that value's *own* key,
not by its container's key. The first version of this helper redacted a value
whenever its parent object's key matched the secret pattern, which sounds
right until you notice `r2_credentials` itself contains the substring
"credential" — that made it collapse into a single `"<redacted>"` string,
throwing away the fact that `CF_ACCOUNT_ID` isn't a secret and hiding which
buckets even have credentials. The fix: always recurse into objects/arrays
regardless of their own key, and only redact leaf (string/number/boolean)
values whose *own* key is secret-shaped.

Second decision, on the `ssh_key_name` ambiguity the sprint flagged: the
secret-key pattern matches `token|secret|password|credential|key`
case-insensitively, but any key that also contains "name" is treated as a
reference (holds a *name of* a key, not a key's value) and left alone. This
correctly exempts `ssh_key_name` / `sshKeyName` while still catching
`R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` (neither contains "name").
Pinned by a dedicated test in `redact.test.ts`.

### Files changed
- (new) `packages/core/src/redact.ts` — `redactSecrets`: deep-clones a value,
  replacing secret-shaped leaf values with `<redacted>`, deciding per-key not
  per-container.
- (new) `packages/core/src/redact.test.ts` — top-level, nested, dynamic-key,
  non-secret-untouched, `ssh_key_name` exemption, no-mutation, and array cases.
- `packages/core/src/index.ts` — exported `redactSecrets`.
- `apps/cli/src/commands/deploy.ts` — `printDryRunPlan` now prints
  `JSON.stringify(redactSecrets(extraVars), null, 2)` instead of the raw
  object.
- `apps/cli/src/commands/deploy.test.ts` — mock for `@emit-infra/core` now
  uses `vi.importActual` to pass through the real `redactSecrets` (was fully
  stubbed, which would've made a printer redaction test pass for the wrong
  reason); added a test asserting the printer omits a fake `ghcr_token` value
  while still printing the key.
