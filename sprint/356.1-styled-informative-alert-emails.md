# Styled, information-rich alert emails: one layout, one renderer per alert kind
**Difficulty:** 4

> _Added by the orchestrator on 2026-10-06 at the user's request, after the
> sprint 356 test email arrived as a bare `<h2>` and one sentence: "make sure
> our future emails will be styled and be as informative as possible with the
> information presented well."_

## Goal
Every alert email emit-infra sends uses one shared, styled layout:
- a severity colour band;
- a clear headline;
- a facts table;
- recent context;
- next-step actions (dashboard link, the CLI command to run, the runbook).

Each kind of alert has its own renderer that fills the layout with the
details that matter for it. Every email also carries a matching plain-text
version. Sprint 357 then wires each alert source to its renderer.

## Reason
The pipeline works (sprint 356), but the default body is `<h2>title</h2><p>body</p>`.
An alert email at 3 AM should answer, without opening a laptop:
- what broke;
- since when;
- how bad it is compared with normal;
- what to run first.

That's the difference between "glance and go back to sleep" and "boot the
Mac to find out". Doing this before 357 means each call site is written once
against a structured renderer, rather than once now and again later.

## Context
- **What 356 built:** `apps/api/src/lib/notify.ts` has `notify(payload)`.
  Its `buildEmail()` uses `payload.emailHtml`, or falls back to a bare
  title/body/link. `NotifyPayload` = `PushPayload` +
  `severity: 'info'|'alert'`, `email?`, `emailHtml?`.
  `apps/api/src/lib/email.ts` has `sendEmail({subject, html, text})` via
  `@develemail/sdk`. The sender is `alerts@develemit.com` and the recipient
  is `ALERT_EMAIL_TO`. `DASHBOARD_ORIGIN` (default `http://localhost:7013`)
  turns relative URLs into absolute ones.
- **Rendering approach (decision):** typed TS string builders with inline
  CSS and table-based layout. No React in the API, so no
  `@develemail/react`. The API is a plain Fastify ESM package with no JSX
  toolchain, and alert mail is a handful of fixed shapes. Email-client rules
  apply:
  - 600px single column;
  - inline styles only (no `<style>` reliance), with a `<style>` block only
    for the optional dark-mode `@media (prefers-color-scheme: dark)`;
  - system font stack;
  - no external images (Gmail proxies and blocks them);
  - buttons as styled `<a>` in a table cell;
  - a hidden preheader span carrying the one-line summary, so the inbox
    preview is useful.
- **Escaping:** every interpolated value goes through one `escapeHtml` that
  also escapes `"` and `'`. Error text and certbot output are untrusted.
- **Tone, separate from delivery severity:** add
  `tone: 'critical' | 'warning' | 'recovered' | 'info'` to the layout input.
  Colours: red `#dc2626`, amber `#d97706`, green `#16a34a`, blue `#2563eb`.
  Severity still decides whether to send at all; tone decides how it looks.
- **Subject lines carry the essentials**, so the inbox list is useful on its
  own:
  - `[emit-infra] 🔴 tastease DOWN — HTTP 502`
  - `🟢 tastease recovered after 14m`
  - `🟠 diner-decider cert expires in 6 days`
  - `🔴 martialops deploy #812 failed`
  - `📊 Weekly fleet digest — 7 projects, 2 incidents`
- **Data already available for context:**
  - incidents: `apps/api/src/lib/incidents.ts` (`.incidents.jsonl`, with
    `readLastIncident`);
  - metric history and trends: `metric-point.ts`, `trend.ts`
    (`computeLinearTrend` for disk/mem), per-project `.metrics.jsonl`;
  - fired alerts: `FiredAlert` in `alert-rules.ts`, enriched by
    `enrichFiredAlert` in `status-monitor.ts` (cert name, certbot error);
  - health causes: `causeText()` and `formatDuration()` in `http-health.ts`;
  - deploy state and history: `routes/deploy.ts` (`.deploy-history.jsonl`:
    sha, branch, buildNumber, durationSec, error);
  - digest: `buildDigest()` in `weekly-digest.ts`;
  - project config (serverIp, domain, healthCheck.url): `discover-projects.ts`.
  Renderers take plain data objects. Gathering the data is the caller's job
  (sprint 357), which keeps renderers pure and snapshot-testable.
- **Times:** show absolute times in `America/Phoenix` (the user is in MST,
  no DST) with a relative hint ("08:50 MST · 14 min ago").
- **File size:** keep every file ≤200 lines. Put the layout and each
  renderer in their own files under `apps/api/src/lib/email-templates/`.

## Tasks
1. `email-templates/layout.ts`: `renderLayout({ tone, preheader, headline,
   summary, facts, sections?, actions, footerNote })` returns `{ html, text }`.
   - `facts` is `Array<[label, value]>`, rendered as a two-column table.
   - `sections` holds optional titled blocks: a key/value list, a short
     table, or a monospace `<pre>` for error output (truncated to about 40
     lines with "…truncated").
   - `actions` holds up to 3 buttons, plus a "Run:" code line for CLI
     commands.
   - The footer shows the timestamp, why the email was sent, and how
     cooldowns work ("next reminder in 6h").
2. Renderers, each returning `{ subject, html, text }`:
   - `health.ts`: SSH/HTTP down, reminder and recovered.
     - Facts: project, server IP, check type, cause and HTTP status, down
       since, duration, last good check.
     - Context: incidents in the last 7 days.
     - Actions: open the project in the dashboard; run
       `emit-infra status <name>`; `/triage-prod`.
   - `alert-rule.ts`: fired rules, one email listing every fired rule for
     the project.
     - Per rule: metric, current value against the threshold, a 24h trend
       arrow and the projected time-to-full for disk/mem from
       `computeLinearTrend`.
     - Cert rules add the cert name, days left and certbot error.
     - Backup rules add the last run time and status.
   - `deploy.ts`: deploy failed.
     - Facts: sha (short), branch, build number, duration.
     - The error goes in a `<pre>` block.
     - Actions: `emit-infra rollback <name>`, the deploy log location, and
       the dashboard.
     - Deploy success stays push-only, so no renderer is needed for it.
   - `digest.ts`: weekly digest.
     - Fleet summary line, then a per-project table: status dot, uptime or
       incidents, deploys, disk % with delta, cert days, backup age.
     - Values outside healthy ranges are tinted amber or red.
3. Extend `NotifyPayload` with `email?: { subject, html, text }` (structured)
   in place of the raw `emailHtml`. `buildEmail()` uses it when present and
   otherwise falls back to `renderLayout` with tone from severity. Move the
   test endpoint to a rich sample.
4. Add `pnpm --filter @emit-infra/api email:preview`, a script that renders
   every template with fixture data to `tmp/email-preview/*.html` and
   prints the paths for a visual check in a browser.
5. Send **one real sample of each kind** to `ALERT_EMAIL_TO` through the
   test endpoint, extended with `?sample=health|alert-rule|deploy|digest`.
   Record the `devel logs` delivered lines in the sprint's Completed
   section. Don't block on the user reviewing them; they review
   asynchronously.

## Completed

**Date:** 2026-10-06

### Summary
Added `apps/api/src/lib/email-templates/`: one table-based, inline-CSS layout (`renderLayout`: tone band, preheader, headline, facts table, optional list/table/`<pre>` sections, up to 3 buttons plus `Run:` lines, footer with MST timestamp and cooldown note) and four pure renderers (`health`, `alert-rule`, `deploy`, `digest`) that return `{subject, html, text}`. Every interpolated value goes through `escapeHtml` (also escapes quotes). Times are shown in America/Phoenix with a relative hint.

`NotifyPayload.email` is now the structured `RenderedEmail` (replacing the `email?: boolean` flag and `emailHtml`): present means email is sent even at `info` severity; absent falls back to `renderLayout` with tone from severity. The manual `POST /push/notify` now uses `severity: 'alert'` (to still email) and supports `?sample=health|alert-rule|deploy|digest`. `pnpm --filter @emit-infra/api email:preview` writes 5 HTML files to `apps/api/tmp/email-preview/`. `scripts/` was added to the api tsconfig include so lint and typecheck cover it.

All four sample kinds were sent for real and show `delivered` in `devel logs`: health (12:02:20), alert-rule (12:07:33), deploy (12:12:49), digest (12:18:07). The alert-rule preview was screenshotted via headless Chrome and looks right; I did not view the Gmail rendering myself, the user reviews asynchronously.

### Follow-ups
- `[blocker]` develemail rejects a second email to the same recipient within 5 minutes (HTTP 429, surfaced by the SDK as the misleading "idempotency key is currently being processed"). Sprint 357 routes every alert through `notify()`, so a burst (e.g. several projects down at once) will drop all but the first email. 357 needs per-project batching or a different delivery approach before it ships.
- `[defer]` `pnpm build` was run during verification; dashboard returned 200 afterwards, but see the clobbered-.next pitfall if pages 500.
