# Verify CLI deploys by image digest, not by one container's build label
**Difficulty:** 3

> _Written after sprint 345's real deploy, to clear its `[blocker]`, 2026-09-20.
> The diagnosis below corrects the fix that blocker proposed — read it before
> choosing an approach._

## Goal
The CLI's post-hoc deploy verification can actually succeed, so `emit-infra
deploy` stops writing a contradictory `isBuildBaseline: false` record beside
every good deploy.

## Reason
Sprint 345 deployed emit-vision and filed this `[blocker]`, verbatim:

> Baseline-flag contradiction on emit-vision: CLI printed `Warning: the running
> image has no build.number label, so this deploy can't be verified — recording
> deployed but not as a build baseline.` … Yet the long history record and
> terminal `.deploy-status.json` say `isBuildBaseline:true` (only the short
> record is false) … Decide: emit-vision adds the label, or the CLI reads
> `org.opencontainers.image.version`, and reconcile which record carries the flag.

**Neither proposed fix works**, and the problem isn't specific to emit-vision.
Both were checked against the live server and the fleet's deploy history on
2026-09-20.

### It has never succeeded anywhere
Every deploy record written since sprint 336, split by who wrote it:

| Project | hook records (baseline true) | CLI records (baseline true) |
|---|---|---|
| develemail | 2 (2) | 2 (**0**) |
| diner-decider | 1 (1) | 1 (**0**) |
| emit-billing | 1 (1) | 1 (**0**) |
| emit-social | 2 (2) | 2 (**0**) |
| emit-vision | 5 (5) | 5 (**0**) |
| martialops | 1 (1) | 1 (**0**) |
| tastease | 7 (7) | 6 (**0**) |

**0 of 18.** That includes emit-billing, which is the one project whose
Dockerfiles *do* bake `LABEL build.number`. So "add the label" is disproven by
existing data before anyone edits a Dockerfile.

This is also the "two records per push" pattern: the pre-push hook writes one
record (carries the real baseline), then invokes `emit-infra deploy`, which
writes a second (always false). Every baseline the path filter actually relies
on comes from the hook.

### Why: it reads an arbitrary container
`apps/cli/src/commands/deploy.ts:303`:

```ts
docker inspect --format '{{index .Config.Labels "build.number"}}' $(docker compose … ps -q | head -1)
```

`head -1` is whichever container Docker lists first. On a path-filtered deploy
most services are **re-tagged**, not rebuilt, and a re-tagged image correctly
keeps the build number it was originally built in. emit-vision after build 1528:

| service | built this deploy? | `org.opencontainers.image.version` |
|---|---|---|
| web | yes | 1528 |
| api | re-tagged | 1520 |
| worker | re-tagged | 1463 |
| marketing | re-tagged | 1463 |

So comparing *any* per-image build label against the deploy's build number is
wrong by design for re-tagged services. Adding `build.number` to more
Dockerfiles, or switching to `image.version`, would read `1520`/`1463` and
reject a perfectly good deploy.

## Context

### The recommended fix: compare digests
The question the check really asks is "is each running container the image we
pushed for this sha?" Sprint 342 already resolves the per-service refs
(`resolveImageName` in `apps/cli/src/lib/image-name.ts`) and probes the registry
(`checkImagesExist` in `apps/cli/src/lib/image-preflight.ts`). Re-tagging
pushes `<image>:<sha>` for re-tagged services too, so **every** service has a
sha-tagged ref.

Compare the running container's image digest (`docker inspect … .Image`, or the
compose `com.docker.compose.image` label) against the registry digest of
`<image>:<sha>`, per service. This works for built and re-tagged services
alike, needs no Dockerfile changes in seven repos, and survives the fleet's
`:latest` compose tags. Confirm the exact digest shapes match before relying on
them — a local image ID and a registry manifest digest are not the same
string, and multi-arch manifest lists add one more layer. If digests prove
impractical, the fallback is to verify **only services in the built set**
against the build label, and say so explicitly.

### Which record carries the flag
Decide whether the CLI should write its own record at all when invoked from the
hook (the hook already writes the authoritative one), or whether the two should
merge. Whatever you choose, a single push must end with one unambiguous answer
to "is this sha a build baseline?" — and `resolve_last_deployed_sha` must still
select correctly. Read how it picks a record before changing either writer.

### File size
`deploy.ts` is 433 lines and `deploy.test.ts` 892, both far over the 300 target
(already on the backlog from sprint 342). The verification logic this sprint
touches is the natural thing to extract — move it into its own module
(e.g. `apps/cli/src/lib/deploy-verification.ts`) as part of the change.

### Conventions
Vitest beside source; externals mocked at the `sshExec` boundary, as
`deploy.test.ts` already does. No `check:affected` here — the suite is
`pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm test:hooks`.
