# Stop execa failures from leaking argv (and the secrets in it) into error messages
**Difficulty:** 2

## Goal
When `ansible-playbook` or `terraform` exits non-zero, the error this repo
throws names the exit code and nothing else. No command line, no
`--extra-vars` JSON, no `-backend-config=secret_key=…` — so nothing
secret-bearing can reach `.deploy-logs/<sha>.log` or a session transcript.

## Reason
Found during sprint 317 while grepping `.deploy-logs/` for token leakage, and
confirmed in a real July 2026 diner-decider failure log. When
`ansible-playbook` fails, the `execa` call in `runAnsible` throws an error
whose `.message` contains the full command line, including the raw
`ghcr_token`. The wrapping deploy script captures that string and writes it to
`<project>/.deploy-logs/<sha>.log` in plaintext.

Verified empirically 2026-08-26 against this repo's installed execa:

```
Command failed with exit code 3: sh -c 'exit 3' --extra-vars '{"ghcr_token":"gho_SUPERSECRET"}'
```

Both `err.message` and `err.command` carry the value.

`no_log: true` on the Ansible task does **not** protect against this. That flag
suppresses *Ansible's own* task output; this is a process-level error string
produced by execa in the Node parent, before Ansible's logging is involved at
all. Sprint 317 added the `no_log: true` login task and this leak still exists.

**This is what gates sprint 320.** Today a leak is cushioned: every fleet
server still has a persistent `/root/.docker/config.json` credential, so the
per-deploy token is not the only thing that works. Sprint 320 removes those
files fleet-wide, making the per-deploy token the *only* live credential — at
which point a single failed deploy writes the sole working credential to disk
in plaintext. Land this first.

## Context

### The bug is in one branch of each function, and the other branch is already correct
Both `runAnsible` and `runTerraform` have two code paths, and only the
`stdio: 'inherit'` one leaks.

`packages/core/src/ansible.ts`:
```ts
if (!onLine) {
  await execa('ansible-playbook', args, { stdio: 'inherit', env })   // ← LEAKS
  return
}

const proc = execa('ansible-playbook', args, { stdout: 'pipe', stderr: 'pipe', reject: false, env })
// ...
if ((result.exitCode ?? 1) !== 0) {
  throw new Error(`ansible-playbook exited with code ${result.exitCode}`)   // ← already clean
}
```

`packages/core/src/terraform.ts` has the identical shape with
`throw new Error(\`terraform exited with code ${result.exitCode}\`)`.

So the fix is to make the leaking branch produce the same clean error the
sibling branch already produces. **Do not invent a new error format** — match
each function's existing string exactly, since callers and tests may match on
it.

### Why suppress rather than redact
A redaction helper has to know every secret-shaped key, and a new caller can
add one it doesn't know about. Not including the command line at all cannot be
missed. Redaction is still the right tool for output we *deliberately* print —
that is sprint 317.2's job, and it is a separate concern.

### Terraform leaks too — a distinct secret, same mechanism
`apps/cli/src/commands/setup.ts:152-156` calls:
```ts
await runTerraform('init', [
  '-input=false',
  `-backend-config=access_key=${stateToken.accessKeyId}`,
  `-backend-config=secret_key=${stateToken.secretAccessKey}`,
], tfDir)
```
Those are R2 backend credentials on argv. `setup` passes no `onLine` callback,
so it takes the leaking branch. A failed `terraform init` exposes them exactly
the way a failed `ansible-playbook` exposes `ghcr_token`.

### Which callers are affected
`stdio: 'inherit'` (leaking) — all three CLI paths:
- `apps/cli/src/commands/setup.ts:264` (`runAnsible`) and `:152` (`runTerraform`)
- `apps/cli/src/commands/configure.ts:46`
- `apps/cli/src/commands/deploy.ts:324`

Already safe (passes `onLine`, so uses the clean branch):
- `apps/api/src/routes/ops.ts:61`

### Preserve the exit code
Callers and the deploy scripts branch on failure, and losing the exit code
would be a regression. Read it off the execa error (`err.exitCode`) and put it
in the clean message. Fall back to a sensible value when it is undefined — the
existing clean branch uses `?? 1`; mirror that.

### Test conventions
`packages/core/src/ansible.test.ts` and `terraform.test.ts` already mock execa
with `vi.mock('execa', …)` and a `makeProc(exitCode, …)` helper. Add to these
files; do not create new ones. To exercise the leaking branch, make the mocked
`execa` **reject** with an error whose `.message` contains a fake secret, then
assert the error surfacing from `runAnsible` does not contain it.

## Tasks

   so a non-zero exit throws `ansible-playbook exited with code <n>` — byte-

   execa's own error propagate.

## Completed

**Date:** 2026-08-27

### Summary
Both `runAnsible` and `runTerraform` leaked their full argv (including
`--extra-vars` JSON and `-backend-config=` values) into the thrown error
whenever the `stdio: 'inherit'` branch failed, because execa's default
`reject: true` behavior surfaces its own error with `.message`, `.command`,
`.escapedCommand`, and `.shortMessage` all carrying the raw command line.
Fixed by wrapping that `await execa(...)` call in each function in a
try/catch that discards the execa error entirely and throws a plain `Error`
with the same message format the sibling `onLine` branch already produces
(`ansible-playbook exited with code <n>` / `terraform exited with code <n>`),
reading the exit code off `err.exitCode` with the same `?? 1` fallback the
existing clean branch uses. No `cause` is set, so no logger can walk a chain
back to the leaky execa error.

Verified the regression tests actually catch the bug (not just pass
trivially) by stashing the two source fixes, re-running the new tests against
the old code, and confirming both failed with the secret value appearing in
the message (`gho_TESTSECRET` / `R2_TESTSECRET`), then unstashing and
confirming both pass.

### Files changed
- `packages/core/src/ansible.ts` — wrap the `stdio: 'inherit'` execa call in
  try/catch, rethrow a clean `ansible-playbook exited with code <n>` error
- `packages/core/src/terraform.ts` — same fix for `runTerraform`
- `packages/core/src/ansible.test.ts` — regression test: mocks execa to
  reject with a leaky error containing `gho_TESTSECRET` and `--extra-vars`,
  asserts neither appears in the thrown error and the exit code is preserved
- `packages/core/src/terraform.test.ts` — same regression test shape for a
  fake `-backend-config=secret_key=R2_TESTSECRET`
