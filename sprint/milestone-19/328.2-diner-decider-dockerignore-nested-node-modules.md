# Exclude nested node_modules from diner-decider's Docker build context
**Difficulty:** 2

> _Written by /start-sprint-auto to clear sprint 328.1's blocker, 2026-09-12._

## Goal
diner-decider's `.dockerignore` excludes nested `node_modules` directories the
way every other repo in the fleet already does, so a Docker build from a
developer checkout that has them installed cannot fail on a path collision.

## Reason
Sprint 328.1 surfaced this as a `[blocker]`: building `apps/api` from the
persistent local checkout fails with

> cannot replace to directory .../node_modules/sharp with file

because the host's symlinked `sharp` under `apps/api/node_modules` and the
container's own hoisted install collide at the same path.

Verified independently before filing this sprint — the claim holds and the fix
is unambiguous, because **diner-decider is the only repo in the fleet missing
the pattern**:

| repo | `.dockerignore` node_modules patterns |
|---|---|
| tastease | `node_modules`, `**/node_modules` |
| develemail | `node_modules`, `apps/*/node_modules`, `packages/*/node_modules` |
| emit-vision | `node_modules`, `**/node_modules` (plus a comment explaining why) |
| **diner-decider** | **`node_modules` only** |

A bare `node_modules` line matches only the context root. `apps/api/node_modules`,
`apps/web/node_modules` and `packages/db/node_modules` all exist in the local
checkout right now, so they are currently being sent into the build context.

This matters beyond the sprint that found it: `scripts/lib/docker-build.sh`'s
`build_image` builds with context `.` from wherever the pre-push hook runs —
the developer's checkout, not a clean clone. So this is a real deploy hazard
whenever those directories are installed at push time, not merely a local
verification annoyance. emit-vision's `.dockerignore` carries a comment about
keeping the `**/` variant alongside the bare one, which suggests the rest of
the fleet already hit this and fixed it; diner-decider was simply missed.

## Context

### The file
`~/projects/diner-decider/.dockerignore`. Line 1 is a bare `node_modules`.
Several other entries have the same shape (`dist`, `.next`, `coverage/`) and
the same latent gap — emit-vision's comment names exactly that set.

Match the fleet. `**/node_modules` (tastease, emit-vision) is the simplest and
is what a new repo would get; develemail's explicit `apps/*/` + `packages/*/`
form is equivalent for this layout. Pick the `**/` form unless something in
the repo argues otherwise, and say which you chose.

### Consider the sibling patterns, but stay bounded
`dist`, `.next` and `coverage/` have the same bare-pattern issue. Including
them is a small, clearly-correct extension of the same fix and matches what
emit-vision's comment describes. Do it **only** if you can state the reasoning
in one line per pattern; do not turn this into a `.dockerignore` rewrite, and
do not touch unrelated entries.

### Verifying — build, don't inspect
The bug reproduces as a build failure, so the fix must be shown as a build that
now succeeds:

```bash
cd ~/projects/diner-decider
docker build --platform linux/amd64 -f apps/api/Dockerfile -t dd-api-ignore:local .
```

Nested `node_modules` must be present locally when you test (they are today —
`apps/api`, `apps/web`, `packages/db`). If they are missing, the bug will not
reproduce and the test proves nothing: run `pnpm install` first so the
condition actually exists. Capture the pre-fix failure verbatim.

Build `apps/web/Dockerfile` too — sprint 328.1 changed it as well, and it has
the same exposure.

### Deploy posture — do not deploy
diner-decider is ~34 commits ahead of its deployed sha and deliberately
unpushed (sprints 328 and 328.1 both left it that way, and it is filed in
`backlog.md`). **Commit only.**

### Conventions
`.dockerignore` is outside the Nx project graph, so `pnpm check:affected` will
likely report no tasks. Report that honestly — the Docker builds are the real
evidence here, not an empty affected run.

## Completed

**Date:** 2026-09-12

### Summary
Added `**/node_modules` to diner-decider's `.dockerignore`, matching the
pattern already used by tastease, develemail, and emit-vision. The bare
`node_modules` line only matched the context root, so `apps/api/node_modules`,
`apps/web/node_modules`, and `packages/db/node_modules` — all present in the
local checkout — were being sent into the Docker build context. That caused
the host's symlinked native deps (e.g. `sharp`) to collide with the
container's own hoisted install at COPY time. Also extended the same `**/`
treatment to `dist`, `.next`, and `coverage/` since they have the identical
per-package leak shape; emit-vision's `.dockerignore` documents this exact
category as a prior gap, so this closes diner-decider's copy of it in one
pass rather than three follow-up sprints.

Reproduced the pre-fix failure verbatim (below) with nested `node_modules`
confirmed present, then rebuilt both Dockerfiles clean after the fix.
`apps/web/Dockerfile`'s build needs its `NEXT_PUBLIC_*` build-args set (its
`metadataBase` URL construction throws on an empty string) — the sprint's
suggested bare `docker build` command omits them, which is a gap in the
reproduction recipe, not a real defect: `.emit-infra.json`'s `buildArgs.web`
list confirms the real deploy path always supplies them. Verified this by
reverting the `.dockerignore` change (`git stash`) and re-running the web
build with `--no-cache`: it hit the identical `metadataBase`/`Invalid URL`
failure with the *old* `.dockerignore` too, proving the web build issue is
pre-existing and unrelated to this sprint's fix, not something the fix
introduced.
